# リファクタリング設計案

基準: develop / 6e11de3、Mod 0.9.156。2026-09-21に現行コードを調査。
本資料は設計のみ。製品コード、schema、ゲーム内挙動はまだ変更していない。

進捗追記（2026-09-21）: 第1段階のテスト基盤を修復。ログ依存のみをホストへ分離し、現行仕様の75項目が成功。本体Releaseビルドも警告0・エラー0。保存アルゴリズム・schemaは未変更。検証範囲と残課題は [テスト説明](../tests/IdentityChecks/README.md) を参照。以下の調査記録は実装前時点のもの。

## 1. 維持する契約

- DLLとMod専用データを外せばバニラへ戻れる。Modによる保存先は `BazaarDecorTransmog.cfg` とそのバックアップ・一時ファイルに限定する。
- バニラのセーブデータ、配置ID、実効果、共有マスタ、共有UI prefabを書き換えない。公式の実オブジェ編集は公式処理に任せる。
- 6スロット、同名プリセット、保存・読み込み・削除、公式の選択肢とフッター、日本語・英語表示を維持する。
- みため終了確認の3分岐、確認前のホバー姿勢、空き読み込みスロットの無反応、ダイアログの閉じる挙動、一覧の位置を維持する。
- CurrentAppearance・プリセット・PreviousValidStateと外部 `.bak` の構成を維持する。
- 実オブジェ変更後、開店・閉店・マップ再入場時のモデル再適用を維持する。
- デバッグパネル・検証専用UIの削除は今回明示的に依頼された変更として扱う。

## 2. 調査時点の検証

- Mod本体のReleaseビルド: 警告0、エラー0。
- IdentityChecks: 実行前のコンパイルで失敗。リンクしている `Presets.cs` が `Plugin.Emit` に依存し、テストプロジェクトにはPluginがない。
- テスト期待値にschema 5、重複名の禁止、バックアップがある破損主ファイルの拒否が残る。現在のschema 9・同名許可・復旧仕様に合っていない。
- `invalid` テストデータはschema 6で、現在は未来バージョンではない。失敗保存の検証として成立していない。
- ユーザーの実機確認済み結果を正常系の基準とする。ビルド成功だけでUnity/IL2CPP上の回帰なしとは判定しない。

### 調査コードに見えるが、そのまま消さない処理

`SlotRuntime.Evidence` は効果全組合せをJSON化するため重いが、適用前後の比較結果でRestoreを実行する安全確認でもある。
ログ削除と一緒には消さない。第一段階では比較を保持する。後に比較対象の縮小を提案する場合は、失う検出能力を明記した別変更として扱う。

`StaticVisualTree`、モデル識別、世代番号による非同期コールバックの無効化、renderer/mesh/materialの復元記録も安全機構として維持する。

## 4. 責務の分離案

最初は既存処理の移動・改名だけを行い、同じ段階で大きなアルゴリズム変更を重ねない。

| 責務 | 分離後の候補 | 主な所有物 |
| --- | --- | --- |
| 起動・Patch登録・運用警告 | Plugin | Mod所有のHarmony、起動成功状態 |
| CurrentAppearanceと編集中の状態 | AppearanceSession | 確定みため、作業コピー、入場時snapshot |
| モデル表示 | AppearanceRuntime / SlotAppearance | スロットごとのclone、元renderer、非同期世代番号 |
| 閉店店舗の表示 | ClosedTentAppearance / ClosedShelfAppearance | 別寿命を持つ閉店モデルの復元記録 |
| 公式編集画面との連携 | AppearanceEditorUi | タイトル・選択肢・ホバー・フッターの一時変更 |
| プリセット画面 | PresetUiController / PresetObjectPreview | 自分のdialog、公式一覧のclone、位置復元 |
| データ形式と永続化 | PresetModels / PresetStorage | schema、検証、読み込み、復旧、保存 |

通常店舗と閉店店舗は寿命と見せ方が異なるため、無理に単一実装へ統合しない。
スロットは `PartsCategory + index` を正式な識別子として維持し、RuntimeIndexの手計算だけを辞書等へ置換する候補とする。

## 5. 公式API・UIの再利用

継続使用するもの:

- UIManager.OpenDialog / CloseDialog、UISelectDialog、UIDefaultDialog、KeyboardManager.ShowRequest。
- UIMenuFooterのガイド再構築、公式のYes/Cancel/Apply/Discard ID。
- 最高売上記録ページのUICustomPartsListItem、pageToCategoryList、SetDisp。
- BazaarCustomItemData.ToPartsCategory / ToPartsCategoryIndex。
- 公式モデルロード通知、カーソル移動、決定アニメーション。

改善候補:

- タイトルとフッターの日本語・英語文字列検索を、対象ページ配下のコンポーネントと所有するtext IDに寄せる。安定した参照を実データで確認できない箇所は今の検索を残し、推測したAPIへ置換しない。
- LanguageManagerのPatchはtableTypeとtextIdの組で限定する。現在はtableTypeを受け取るが判定に使っていない。公式の名前入力IDは自分の要求中だけ適用する。
- 完了通知のキャンセル許可は現在「自分の通知が開いている」という全体フラグだけを見る。対象dialogのinstance・infoIdも確認する設計へ。
- 完了通知の探索も「最後に見つかったアクティブなUIDefaultDialog」から、自分が開いた通知のIDとinstanceへ絞る。
- オブジェ終了確認の選択監視も、全dialogの存在検索ではなくOnDecideの対象instanceが公式infoId 116000かを確認する。IL2CPPのキャスト方法はビルドと実機で確認する。
- 一覧の11行固定・子階層の取得順は、公式の行リストとカテゴリ対応が取れる範囲で整理する。未知の構造で推測して別カテゴリを表示せず、プレビューだけを停止する案は異常時変更として扱う。
- 390 / -420などの配置値はまず名前付き定数にまとめる。サイズ自動計算へ変えると見た目が変わるため、今回の初期段階では数値と配置を維持する。

既に公式UIを利用しているため、独自UIへの全面置換は行わない。

## 7. 復元と例外の設計

現状、Plugin.Guardは警告して戻るだけでModを無効化しない。またPatch登録途中の失敗では登録済みPatchを戻していない。

提案する障害境界:

1. ファイル読み込み失敗: 既定の空のみためへフォールバックし、元ファイルを保持。既存の復旧データが使える場合は現行の復旧優先順位を維持する。
2. 単一モデルの失敗: 該当スロットのcloneを消し、記録したrenderer/mesh/materialを復元する。別スロットの失敗を巻き込まない。
3. Mod UIの失敗: 自分のUIだけを後始末し、タイトル・フッター・選択肢・位置を復元する。他Modや公式の前面dialogを一律Closeしない。
4. 起動失敗・回復不能なMod状態: 新規操作と非同期適用を停止し、各復元を独立したtryで試行する。起動途中なら自分のHarmony IDだけを解除する。

稼働中の一括Unpatchは、開いているMod通知のキャンセル経路も消してしまう。UIの閉じる経路を維持して後始末を先に実行し、復元失敗は別警告として残す。

PresetUiProbe.EndPresetUiは一部の状態のみ初期化している。slotMenuOpen、nameInputOpen、finishPresetAfterName、returnToSaveSlots、shiftedDialog、close後の継続callback等も含め、通常終了と強制中断を分けて所有物を洗い出す。
古い非同期callbackが新しい画面を開かないようセッション世代番号を導入する候補とする。通常の選択後callbackを止めないよう遷移単位で検証する。

この節の強制無効化・復旧不可時の操作制限は異常系の動作変更を含む。コード整理とは別段階で理由・影響範囲を再確認してから実装する。

## 8. 保存データの安全性

保存形状はschema 9を維持し、クラス整理だけではschemaを上げない。未知のJSONプロパティは現行のSystem.Text.Jsonによる無視を維持する。
既存のschema 1〜9対応と、UiSlotIndexなしの旧レコードを初回整理で削除しない。CurrentAppearance未設定時の既存フォールバックも勝手に変えない。

調査で見つかった注意点:

- LoadFileはschema検証失敗後にPreviousValidStateがあればMath.Clampで既知schemaに変換して復旧できる。将来schemaを誤って読み書きする可能性がある。
- Loadは任意の例外で外部bakを読むため、将来schemaの主ファイルから旧bakへ戻り、後で主ファイルを上書きできる可能性がある。
- Saveも入力SchemaVersionを検証前に9へ変える。未来データを入力した場合に拒否できない。
- 主ファイルを埋め込みsnapshotから復旧してpreviousを得た場合、File.Copyは復旧済みデータではなく元ファイルそのものをbakへコピーする。
- 一時ファイル検証はあるが、バックアップ更新と本体置換の途中失敗、復旧後の保存は追加検証が必要。

安全性改善案:

- 将来schemaを「破損」と分け、復旧・上書きせず保存をブロックする。Mod表示はバニラに戻す。
- PresetStorageをUnity/Pluginから独立させ、読み込み元と復旧理由を結果として返す。運用ログは呼出し側が担当する。
- 一時ファイルへの書き込み、再読込検証、置換の順序を保持する。既存ファイルが正常な場合の置換・bak生成はFile.Replaceも候補とし、復旧元の扱いを含め失敗テストで検証する。
- 既知の正常バックアップを破損ファイルで上書きしない。途中失敗時は現行データのメモリ上の確定も行わない。

これらは通常保存の仕様を維持するが、未来schemaと破損時の扱いを厳密化する変更。先に仕様として合意する対象とする。

## 9. 実装順と検証

1. **検証基盤**: PresetStorageのログ依存を分離。現行仕様にテストを合わせ、正常保存・同名6スロット・CurrentAppearance・旧schema・復旧・保存失敗の基準を作る。
2. **調査コードの削除**: 正常系ログ、未登録Patch、ID探索、検証画像を削除。機能を持つProbeは維持・改名する。
3. **デバッグパネルの削除**: Drawから機能上必要な更新を移してOnGUIと専用入力を削除。外見選択・詳細欄・名前入力を確認する。
4. **責務整理と低リスク軽量化**: ファイル分割、定数・ID整理、セッション単位の参照保持、一時リスト削減。同じタイミングを保つ。
5. **異常系の安全性**: 第7・8節の内容を確認したうえで、Patch登録失敗、部分復元、将来schema、破損・保存失敗へ対応する。
6. **回帰確認と資料更新**: 下記の実機経路を通し、削除理由・置換先・リスクの実績を記録する。READMEの現行機能説明も更新する。

各段階の確認が済んでから次へ進める。実装時のcommit/pushは改めて指示された範囲で行う。

### 自動検証

- Mod本体Releaseビルド、純粋な保存・ID照合テスト。
- 同名プリセット、6スロット、旧プロパティ残存、未知プロパティ、各既知schema。
- 主ファイル破損、埋め込みsnapshot破損、bak破損、両方破損、未来schema、復旧後の再保存。
- 一時ファイル作成不能、本体置換不能などで既存本体・正常bakが保持されること。
- IDの再利用・モデル名の重複が別オブジェの誤表示にならないこと。

### 実機回帰

- 日本語/英語、コントローラー/キーボードの保存・名前変更・読み込み・削除・完了通知・キャンセル。
- 空き読み込みスロット、6番目ラベル、一覧の閉じる位置、再表示、タブ切替、プレビュー。
- みため終了確認の3選択肢 × 浮いている/着地している状態。編集なしの終了も含む。
- オブジェ編集の終了3選択肢、Xガイドの抑止と公式Yとの復帰同期。
- 全配置の実オブジェ変更 → 編集終了 → 開店 → 閉店 → マップ再入場 → ゲーム再起動。
- 棚の商品・販売ポイント・実効果が維持され、ModのDLL/データを外した起動でバニラに戻れること。
- BazaarDecorPresets併用は相手側のUI完成後に確認。他の公式dialogや命名処理への干渉も確認する。

## 10. 初回には行わないこと

- 試験で必要性が分かった小型通知のデータ契約、instance本文補正、キャンセル経路の全面置換。
- 公式非同期処理を即時化すること、ホバー/着地のタイミング変更。
- レイアウトの自動再計算、スロット数や名前長の変更、保存形式の全面移行。
- 必要性を検証せず全Patchを削減することや、別寿命のモデルを共通化すること。
- 過去のdocs調査記録の削除。履歴資料として保管し、現行仕様との違いを明示する。
