# プリセットUI通知の保護（0.9.177）

- 選択通知のセッション内使い回しを廃止。再表示前の通知や重複通知を区別できないため、画面ごとの受付番号へ置換した。副作用より先に受付を消費する。
- 通常Closeを共通の待機処理へ集約。Close完了は遷移の有効性にかかわらず待機を解除し、スロット位置を復元する。待機中は完了メッセージの非表示による自動終了を実行しない。
- 障害時のCloseも同じ待機管理を使い、通常Closeとの重複を防ぐ。送信済みCloseが例外を返しても、開始済みの可能性があるため待機を勝手に解除しない。
- Y削除は入力元の所属ダイアログと公式の現在のダイアログが対象一覧と同一の場合だけ受け付ける。
- プリセット操作中の追加Start入力でメニューを二重に開かない。

保存形式・バニラの実効果データは変更しない。Presetsプロジェクトは参照のみ。

## 確認

Releaseビルド成功。既存97チェックに、古い通知・重複・失効・再入・Close完了と遷移失効の分離を検証する4チェックを追加し、101チェック成功。
これらは管理コードの受付規則の検証であり、Unityの通知順序は実機確認が必要。

影響が出うる箇所：保存/読み込みの往復、名前入力の取消と再入力、削除後の一覧復帰、完了メッセージの連打、空きスロットの決定、Y削除。0.9.177はユーザーによる実機確認済み。

## 0.9.178：Close通知欠落時の終了確認

対象ダイアログとUIManagerを追跡する。Close呼出しが例外を投げた場合に限り、対象が破棄または非表示になり、公式のIsDialogもfalseになったことを確認すると、完了通知なしでも待機を解除してMod UIを中止・後片付けする。遅れて届いた通知は消費済みとなり遷移しない。通常Closeの最後の通知を先回りして中止しないため、例外なしの場合は従来の通知を待つ。

待機を無条件に解除すると二重Closeで別UIを閉じるおそれがあるため、時間による解除・再Closeは行わない。公式UIが残ったままClose自体が停止するケースは、安全な完了判定ができず待機を保持する。このケースの完全な復旧を保証する変更ではない。

自動検証：終了途中を解除しないこと、通知欠落を一度だけ回収すること、古いCloseで次の待機を解除しないことを追加。Unityの例外注入は未実施。
